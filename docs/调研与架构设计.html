结论：空白点在哪里

没有一个开源项目同时做到这四件事

① 跨多个教学平台（学习通 / 雨课堂 / iSmart 一起看）· ② 聚合的对象是作业与考试（有截止时间、需要行动）· ③ 是持续同步而非一次性导入（平台会改期、会加新作业）· ④ 适配器真正插件化（新平台零侵入）

课表类工具占住了「时间维度」，单平台助手占住了「自动化」， 而「我这一周到底要交什么」这个最痛的问题，还没有开源方案回答。

可以放心借鉴的

适配器抽象（WakeUp 的 Parser 范式）· 跨平台桌面选型（ClassIsland 验证了 Avalonia， 而 Tauri 2 在 2026 年已成为轻量跨平台的成熟选择）· cookie 复用降低风控（SuperStarInfoFetch）· 多端共用一份核心（yuketang-helper-auto）。

要主动避开的

现有单平台脚本的重心多是自动作答 / 刷课。这既有明确的合规与学术诚信风险， 在工程上也是死路：一旦涉及提交，就必须对抗平台的签名与行为检测（iSmart 的 ut 就是活例子），维护成本极高且随时失效。

本项目严格限定为只读聚合 —— 只读取作业与考试信息并提醒你， 把「做不做、什么时候做」留给你自己。这既规避了风险，也让工程复杂度下降一个量级。

04技术难点与实现

下面五条全是实际写代码时踩出来的，不是纸上推演。每条都附症状与解法。

难点一 · 截止时间归一化

各平台对「什么时候截止」的表达方式完全不同，这是全项目最脏的一层：

来源原始形态陷阱
超星2026-09-25 23:59是本地墙上时间，用 Date.UTC() 解析会整体偏移 8 小时
雨课堂endTime: 1758815940000epoch 毫秒；但也有接口给纯剩余秒数，靠数量级区分
雨课堂（部分）'还剩 3 天'最大的坑，见下
各平台未公布 / 不限时 / ""是「开放态」，不等于「未知」

最隐蔽的坑：相对截止时间没有锚点，任务永远到不了期

平台返回「还剩 3 天」。如果每次同步都按「当前时刻 + 3 天」重新解释， 那么第五天看它还是「还剩 3 天」—— 提醒永远不会触发，排序永远是最后，这个作业在你眼里永远不紧急。 而代码层面看不出任何异常。

任务静止在「还剩 3 天」；提醒窗口永不命中；截止排序永久排末位 首次观测时把它锚定成绝对时刻（UnifiedTask.deadlineAt），之后一直沿用。 并且只在倒计时变大（真改期）时才重新锚定 —— 变小只是时间自然流逝，不算变更， 否则每天同步都会产生一次假的「截止时间已变更」。

难点二 · 幂等合并（本项目真正的核心）

一次同步拿到几百条任务，反复跑不能产生重复记录，也不能产生无意义的写操作。 mergeTasks() 是纯函数，所以能完整单测。

主键两级策略

// 第一级：平台给了稳定 ID 就用，稳定且免费
// 第二级：兜底指纹（标题先归一化，剥离「（第2次）」这类噪音后缀）
fingerprint = sha1(platformId, courseId, kind, normalizeTitle(title))

// 关键：指纹不含 status 与 deadline ——
// 「交了作业」「老师改期」都应表现为「变更」，而不是「新建一条」

坑 2-1 · 主键必须包含账号维度

同一个平台可以挂多个账号（两个学校的学习通、两个班的雨课堂）， 而平台内 ID 只在平台内部唯一。

两个账号的 work_88001 生成了同一个主键，互相覆盖 platformId + hash(accountId) + platformTaskId。 账号段用哈希而非明文，因为主键会出现在 URL、日志与 UI 里。这条是单元测试跑出来的， 不是想出来的 —— 测试「跨账号互不干扰」第一次就失败了。

坑 2-2 · 上游抖动不能被误判成删除

分页请求失败、临时风控、接口超时，都会让某一轮同步「少看到」一些任务。 如果立刻删库，用户会看到作业一闪一闪地消失又出现。

某轮翻页失败 → 30 个待办瞬间消失 → 用户以为被清理了 连续缺席 N 轮（默认 2）才软删除，且保留记录可被上游恢复； 数据不完整时（翻页中断 / 达到翻页上限 / 演练模式）整轮禁用删除判定。

坑 2-3 · 时间戳精度不一致会刷出假变更

平台返回的时间戳精度不统一（有的到秒、有的到毫秒），直接比较会把每一轮同步 都判定成「截止时间变了」，于是 revision 无限增长、提醒被反复重置。

每 30 分钟同步一次 → 每 30 分钟一条「截止时间已变更」通知 比较前先按 1 分钟粒度对齐，低于该粒度的差异视为噪音。

难点三 · 平台改版必须响亮失败

这是本类应用最严重的故障模式

平台的 HTML/JSON 一改版，解析器就可能「成功地」返回 0 条记录。 从代码角度没有任何报错，从用户角度是「我的作业不见了」—— 他会以为这周没作业，然后错过截止时间。

所以适配器返回空结果、而上游声明有数据时，必须显式抛 SCHEMA_DRIFT。 同时引擎不清空本地数据，用户看到的仍然是上一次同步的正确结果， 加上一条「平台可能已改版」的提示。

▌ 场景 7 · 平台改版（字段改名） ✓ 同步状态为 failed ✓ 错误信息明确指出是结构改版 mock 页面/接口结构可能已改版：预期字段 list 为数组，实际为 undefined （响应键：total,dataList） ✓ 本地数据未被清空 仍为 9 条

难点四 · 提醒的去重与补发风暴

问题如果不处理解法
幂等 同步每 30 分钟一次，只按「是否进入 24 小时窗口」判断 → 一天被提醒 48 次 提醒 key = sha1(任务, 规则+窗口, 截止时间)，发过就记档
改期 旧提醒已失效，但记档还在 → 新截止时间不再提醒 把截止时间编进 key，改期后 key 自然不同，不需要额外的重置逻辑

逾期刷屏 三个月前没做的作业每天提醒一次 逾期超过宽限期（默认 3 天）不再提醒

难点五 · Native 签名（iSmart 的 ut 字段）

iSmart 把签名逻辑编译进了原生 so/dll，社区验证只能靠 unidbg 之类的框架 直接模拟执行那个 so 才能算出来。纯 JavaScript 拿不到签名，而签名不对后端就不认。 这是无法用 TypeScript 解决的问题，硬做只会把整个项目锁死在某个平台。

架构对策：把签名抽成可替换的端口 NativeSigner。

interface NativeSigner {
  available(): Promise<boolean>
  sign(req: { payload: Record<string, string>; algorithm: string }): Promise<string>
}

// ① SubprocessSigner —— 通过 stdio 的 JSON 协议调用外部可执行文件
//    选进程边界而不是静态链接，为的是：
//    · 崩溃隔离：unidbg 跑在 JVM 里，内存占用大且容易出问题，不能拖垮同步进程
//    · 许可隔离：签名组件常是 GPL 或来源不明的二进制，进程调用不构成许可传染
//    · 可替换：用户能换成自己的实现，只要遵守同一份协议

// ② UnavailableSigner —— 没有签名能力时显式失败，绝不返回假签名
降级设计：只读提醒模式

没有签名组件的 iSmart 用户不会「什么都用不了」—— 他仍然能看到已经同步过来的作业和截止时间，只是不能重新拉取或提交。 这个降级比「要么全能要么不能用」友好得多， 也让项目的核心价值（聚合提醒）不被最弱的那个平台拖累。

附带 · HTTP 层的两个隐蔽细节

手动跟随重定向

Node fetch 自动跟随重定向时，中间跳转收到的 Set-Cookie 会被丢掉。 而超星/雨课堂的登录链路恰恰是「POST 登录 → 302 到主页 → 主页下发会话 cookie」。

自动跟随会拿到一个「登录成功但没有会话」的诡异状态 自己接管重定向，跨跳转累积所有 Set-Cookie。

限流不能只在适配器层做

429 时如果只 sleep 这一次，后续请求仍然全速打过去，风控只会升级。

把 Retry-After 回灌给限流器（清空令牌 + 进入冷却），后续请求自动降速； 退避用全抖动指数退避，避免多账号在同一时刻齐步重试形成新尖峰； 401/403 不重试（重试也不会变好，只会浪费额度、加剧风控）。

05「不会影响你正常使用平台」凭什么是真的

这是这类工具最该被追问的一点，也是本项目的第一条设计前提。 关键在于：它不能是一句宣传语，必须是运行时强制、可被测试断言的约束。

机制一 · 只读守卫（HTTP 层强制）

守卫包在传输管道的最外层：只读守卫 → 限流/重试 → 真实传输。 适配器拿到的就是被包装过的客户端，没有办法绕过。

规则内容为什么这样设计
Rule 1 默认只允许 GET / HEAD 绝大多数平台的查询都是 GET，先把面收窄
Rule 2 任何非安全方法必须在适配器的 readOnlyPolicy.allowPost 里逐条声明并写明用途 这份清单本身就是审计材料：想知道这个 app 一共会发多少个"写请求"？ 把各适配器的 allowPost 读一遍即可，通常只有 1~3 行
Rule 3 兜底黑名单命中即拒绝，优先级高于白名单 一处配置失误不应该能破坏整个承诺 —— 即使有人误把提交类路径写进了白名单，也拦得下来

黑名单里那些容易被忽视的路径

显式的 submit / handin / qiandao 大家都想得到。 真正需要警惕的是下面这三类 —— 它们都不是「作弊」，但都会在用户不知情的情况下 改变他在平台上的状态： 

// ① 已读回执 —— 会改变通知状态，让用户以为「我已经看过了」
/(mark-?read|markread|read-?receipt|notice-?read|set-?read)/

// ② 学习行为打点 —— 会让平台记录"你在学"，污染学习数据
/(study-?record|watch-?log|heartbeat|progress-?report|log-?study|play-?log)/

// ③ 退出登录 —— 一旦调用，用户自己在浏览器里也会被登出
/\/(logout|signout|sign-out|exit-login)/

另外还要拦 URL 参数里的动作（?action=submit）—— 很多平台把动作放在 query 里，光看方法分不出来。

机制二 · 会话来源策略（绝不替你重新登录）

「重新登录」本身就是一次影响正常使用的动作

会话失效时，一个看起来最自然的补救措施是「用账号密码再登一次」。 但重新登录 = 在服务端创建一个新会话，而多数平台是单点登录或会轮换 token —— 那会把用户手机上正在用的那个会话顶下线，或者在别的设备弹出「新设备登录」提示。

用户会把这件事归因于「这个破 app 把我挤下线了」， 而且他根本不会想到原因出在我们这里。

所以会话带一个来源标记，它决定了会话失效时我们能做什么：

来源含义会话失效时
imported 用户从浏览器 / 官方客户端复制出来的 永远不用账号密码去重新登录。只报错，把决定权交回给用户
derived 我们用账号密码独立登录取的 允许用户重新登录（并在 UI 上提示可能与官方客户端互踢）

用户看到的提示是这样的： 「会话已被平台失效。我们不会替你重新登录 —— 那可能会把你正在使用的浏览器/App 顶下线。 请你在浏览器或官方客户端里重新登录后，把新的会话凭证粘贴过来。」

两处工程细节

① 引擎从不保存明文密码，所以它在物理上就没有「自动续期」这个能力。 但这条规则仍然以注释形式写在 #ensureSession() 上， 因为将来如果有人想在这里加自动续期，必须先读那段话。

② 提示语集中在一处生成。 会话失效可能在过期探测、拉课程、拉任务三个地方被发现， 如果各写一遍就会出现「有时候说得很清楚，有时候只丢一句 401」—— 而这句话直接决定了用户接下来做什么，不能时有时无。

429 的 Retry-After 回灌限流器不是只 sleep 这一次，而是后续请求整体降速
全抖动指数退避避免多个账号在同一时刻齐步重试，形成新的尖峰
401 / 403 不重试重试也不会变好，只会浪费请求额度、加剧风控

这条承诺是可验证的

假教学平台里放了一个「危险端点」诱饵（POST /submit， 在真实场景里它提交作业答案）。测试主动去尝试提交它， 然后断言被拦下、且服务端记录中该请求从未出现。

一个从没被尝试过的保护措施，等于没有保护措施

只写「我们不会提交作业」是不够的 —— 必须有代码去试图违反它， 并且失败。这是这段测试存在的全部意义。

上面三层机制把影响压到最低，但严格说仍是「少发请求」。 再往下还有两级，关键洞察是：把传输层做成 HttpClient 的替身， 任何适配器零改动就能换载体。

路线 A · HAR 录制与回放

record 命令把一轮同步的响应固化成标准 HAR（默认脱敏且不可关闭 —— HAR 里天然含 Cookie 与 Authorization，那是完整登录凭证，而回放只需要响应体）； import-har 则是一个一个真实请求都不发的传输， 适配器照常「请求」接口，拿到的是上次抓包的响应。 

# ① 录制（也可以直接用浏览器 DevTools 导出 HAR）
node apps/cli/src/main.ts record chaoxing 账号 密码 --out capture.har

# ② 之后任何时候离线回放 —— 平台甚至可以完全不在线
node apps/cli/src/main.ts import-har chaoxing capture.har

路线 B · CDP 附着（凭据不过手）

请求是在用户自己的浏览器标签页里发出的，用浏览器自己的会话： 不创建任何新会话；cookie 由浏览器自动附带， 而 HttpOnly cookie 对页面 JS 不可见 —— 我们连读都读不到，更不可能存。

这也是 iSmart 这类「客户端是套壳 Chromium」的平台唯一现实的只读路径 —— 社区的 iSmartAuto 就是这么发现客户端可以加 --remote-debugging-port 的。 区别在于：他们用它提交答案，我们只用它读取作业。

踩出来的坑：离线路径必须显式圈定范围

import-har 最初实现时调的是 syncAll()（不带参数）， 结果引擎把库里所有账号都同步了一遍 —— 包括挂着真实会话的账号， 「零网络请求」的承诺被一行代码悄悄破坏了。

两条离线命令都强制传 accountIds: [account.id]。 默认行为是全局的，而全局行为对离线场景是危险的。

边界：做不到的部分（诚实交代）

① 无法 100% 保证零影响

平台的风控是黑盒且持续变化。我们能做的是「最小侵入」—— 低频 + 只读 + 复用用户自己的会话，但不能承诺零影响。 如果平台把「同一 cookie 在不同 UA/IP 下并发请求」判为异常，我们无法预知。

② 会话失效是必然的

用户在手机上点了退出登录、或平台策略性地轮换 token，导入的会话就失效了。 这时会提示重新粘贴凭证 —— 这是设计，不是缺陷。

③ 不要和官方客户端同时高频使用

部分学校明确禁止账号共享。同时高频使用理论上存在被平台判定为异常的风险， 这点需要用户自己评估。

一个更「零影响」的备选形态

如果连上面这些都想避免，还有一个几乎零侵入的方案：做成浏览器扩展。 它直接复用用户浏览器里已有的会话，不新建任何登录，请求也来自用户正在浏览的那个浏览器。 代价是只能读用户打开的页面、移动端不可用。 核心库一行都不用改 —— 只是换一个壳层（适配器的输入从 HTTP 响应变成页面内容）。
