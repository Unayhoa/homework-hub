# 超星任务点统计 · 方案 v1

> 状态：**阶段 1 已实现（v0.2.31，仅展示）**。提醒暂缓 —— HAR 证实这两个页面里没有截止时间。
> 需求来源：部分课程要求完成任务点学习并计入最终成绩，用户需要知道「这门课还差多少」。

## 0. 取证结论（2026-11-02，HAR 实证）

抓包工具：`mooctest.chaoxing.com.har`（523 条，进入课程 → 点章节 → 进入任务点的完整动作）。

## 1. 判据

一条数据该不该进「待办」，取决于**它有没有"要行动的时刻"**。

- 作业 / 考试：有截止时间 → 进待办，按时间分组、按 deadline 提醒。
- 任务点：多数是学期内慢慢累积（18/30），但也有课程设了较早的章节截止。

⇒ 结论：**任务点不是作业的同类，但它里面确实有一部分带时间**。方案必须同时容纳这两种。

## 2. 结论摘要

| 决策 | 选了 | 备选 | 为什么 / 选错的代价 |
|---|---|---|---|
| 展示粒度 | **课程级汇总**（18/30 · 60%） | 章节级 / 单任务点 | 单点级要逐章节请求，成本翻几倍；课程级已能回答"还要不要管" |
| 采集粒度 | **章节级**（只用来算"最近截止"，不展示） | 纯课程级 | 他的需求里有"提醒即将截止"，课程级汇总没有时间轴可用。同一响应通常就带章节，几乎不加请求 |
| 入口 | **待办二级 tab**（复用 `.seg-tabs`） | 课程页 / 新一级 tab | 他明确选了这个；数量少（手动添加），不会撑爆徽标 |
| 徽标 | 一级「待办」**只算作业/考试**，不变 | 把任务点也算进去 | 算进去会让「还有 14 件要做」变成 60+，这个直觉是待办页唯一的价值 |
| 课程筛选 | **默认不添加，手动勾选**；添加时给"检测到 N 个任务点 / 最近截止"辅助判断 | 默认全显示 | 他判断有需求的课程很少；且任务点数据是主动成本（见 §8），不该默认承担 |
| 刷新 | **添加时探测全部；已添加课程 24h TTL** | 每轮同步都抓 | 32 门课 × 1 请求 = +60% 请求量，而它是慢变量 |
| 提醒 | **复用现有提醒管线**，键换成课程 ID | 只做界面上变色 | 他很少打开这个 tab，只变色等于没有提醒 |

## 3. 数据模型

挂在课程上，不新建实体：

```ts
// domain/course.ts
export interface CourseTaskPointProgress {
  /** 任务点总数 / 已完成 —— 平台口径，不做二次推算 */
  total: number;
  done: number;
  /** 最近一个**未完成**章节的截止时刻（ISO）。没有未完成章节 / 平台不给 → 不写这个键 */
  nextDueAt?: string;
  /** 上面那个截止属于哪一章，用于提醒文案（"第3章还剩 2 个"） */
  nextDueChapter?: string;
  /** 抓取时刻。用于展示"数据较旧"，不用来做 TTL 判定（TTL 靠游标） */
  fetchedAt: string;
  /**
   * 此刻**还能做**的任务点条数（v0.2.44）。只统计「待完成任务点」标记所在、
   * 且此刻已开放的章节 —— 未开放 / 已关闭的章节即使还没做完也不算。
   * 取不到或无法归属到章节时不写这个键，界面退回"还有可做的"，绝不编数字。
   */
  availableNow?: number;
}

export interface UnifiedCourse {
  // ...现有字段
  /** 任务点进度（可选）。不写这个键 = 没抓过 / 该课不需要统计 */
  taskPoints?: CourseTaskPointProgress;
  /** 用户是否把该课纳入任务点统计。true 才显示在任务点 tab 里 */
  taskPointTracked?: boolean;
}
```

**为什么不是新表**：任务点进度的生命周期和课程完全一致（课程在它就在，课程没了它就该没），而且永远只按课程查询。单开一张表等于多一处「课程删了进度还在」的清理逻辑。

**⚠️ 实现坑（必须写进代码注释）**：`upsertCourses` 是 `{...prev, ...c}` 合并写入，
所以同步课程时**不能**在 mapped 对象里写 `taskPoints: undefined` —— 那会抹掉上一轮抓到的进度。
同理 `taskPointTracked` 是**用户意志**，同步永不许覆盖（与 `displayName` 同一条规矩）。

## 4. 采集通道

### 3.1 形态：可选能力，不进 `fetchTasks`

```ts
// ports/adapter.ts
export interface PlatformAdapter {
  // ...
  /**
   * 抓「课程级任务点进度」。可选能力 —— 不实现 = 该平台没有这个概念。
   * 独立于 fetchTasks 的三个理由：
   *   ① 刷新节奏不同（天级 vs 分钟级），塞进主同步会让每轮都背上 32 个请求
   *   ② 失败不该影响作业同步（它只是附加统计）
   *   ③ 它产出的不是 task（没有 deadline 语义的累积指标）
   */
  fetchCourseProgress?(
    ctx: AdapterContext,
    session: Session,
    courses: UnifiedCourse[],
    req: { courseIds?: string[] },
  ): Promise<Page<CourseProgressItem>>;
}
```

`CourseProgressItem` = `{ platformCourseId, total, done, nextDueAt?, nextDueChapter? }`。

### 3.2 触发

| 时机 | 抓谁 | 说明 |
|---|---|---|
| 用户打开「添加课程」列表 | **全部课程** | 一次性，用户主动触发。不知道哪些课有任务点，就无法让用户勾选 |
| 同步时，距上次 > 24h | **仅已添加的课程** | 通常 1–3 门 |
| 用户手动刷新（tab 内下拉/按钮） | 仅已添加的课程 | 刚刷完课想立刻看到数字变化时用 |

TTL 用游标存（`kind: 'course-progress'`），与现有 `course-crawl` 同构。

### 3.3 失败处理

- 单课失败 → 跳过该课，保留上一次的数值，日志里记一条
- 全部失败 → 日志 details 报错，**不动已存的进度**（宁可显示旧数字，不要显示 0/0）
- `0/0` 是非法值：`total === 0` 时视为"该课没有任务点"，不显示卡片

## 5. 展示：待办二级 tab

复用记录页的 `.seg-tabs` 组件，不改结构：

```
[待办 14]
  ┌──────────────────────────────────┐
  │  作业 14  │  任务点 2             │   ← seg-tabs
  └──────────────────────────────────┘
  「作业」段：现有时间分组，一行不动
  「任务点」段：课程卡列表
```

**卡片形态**（课程级，不展开章节）：

```
[数据结构] 25级数据结构
任务点 18/30 · 60%
▓▓▓▓▓▓▓▓▓░░░░░
最近截止 · 第3章 11/20 23:59        ← 有才显示；7 天内黄、3 天内红
                                      已更新 3 天前
```

- 排序：按**状态严重度**（逾期 → 倒计时中 → 未开放 → 无期限 → 已完成），同级按课程名
- 卡片文案只有四种（v0.2.35）：

  | 状态 | 文案 | 进度条 | 依据 |
  |---|---|---|---|
  | 已全部完成 | `已全部完成` | 绿 | `done >= total` |
  | 错过 | `还差 2 个 · 章节已于 10/18 关闭` | **红** | 有 `lastClosedAt`、无 `nextWindow` |
  | 正在倒计时 | `现在可做 8 个 · 12/12 关闭 · 11/23 开新章` | 紫（7 天内黄、3 天内红） | `hasOpenNow` + `availableNow` + `nextWindow` |
  | 现在没得刷 | `还差 26 个 · 11/8 开放` | 灰 | `hasOpenNow=false` + `nextWindow` |

  > **v0.2.44 起，倒计时/可刷的文案带上「现在可做 N 个」**：`done/total` 是整门课的
  > 累计差，里面含着还没开放和已关闭的章节，不能拿它当"现在能做几条"。
  > `availableNow` 只算已开放且还有未完成点的章节。页面认不出章节归属时不给数字。

- **不显示章节名**：一个章节名对"要刷多少 / 什么时候截止"没有任何帮助，
  却占掉整行最值钱的位置（用户原话：「时间前的章节名没有存在意义」）。
  而且它本来就不稳定 —— 选的是"最快关闭"的窗口，同一天关闭时取页面上第一个，
  也就是章节序号最小的那个，纯属任意。
- 全部完成的课：**保留**，置灰排最后（他要能确认"这门搞定了"）
- 平台没有 `fetchCourseProgress` 或一门课都没添加 → 段内显示空状态，不隐藏 tab
  （隐藏会让"我明明加过"变成找不到入口）

**空状态 = 添加入口**：

```
还没有添加课程
任务点统计只对你在意的课程开启 —— 有些课的任务点不计入成绩
[＋ 添加课程]
```

## 6. 课程筛选：手动添加 + 探测辅助

点「添加课程」→ 触发一次全量探测 → 弹层列出候选：

```
检测到 6 门课有任务点
☑ 数据结构          42 个任务点 · 最近截止 11/20
☐ 大学物理          18 个任务点
☐ 英语视听说        96 个任务点 · 最近截止 11/15
```

勾选即写入 `taskPointTracked: true`。

**这就是"辅助判断"的落点**：用户判断"要不要刷"靠的是老师说过什么，但他不知道
"这门课到底有多少任务点、什么时候截止"。把这两个数摆出来，判断就从猜测变成核对。

**默认全部不勾** —— 与"默认偏显示"相反，理由不同：
- 任务点的成本是**主动的**（探测请求是用户点出来的，后续还有每 24h 的刷新）
- 而「漏掉一门」的代价是期末发现进度不够，所以候选列表必须**完整**（不能漏课），
  但不该替用户默认开启

> 取舍记录：一开始想"默认全显示"（代价不对称：漏掉=挂科）。
> 改成"默认不添加"是因为他的判断是「有需求的课程较少」——
> 那么默认全开会把 30 门课全塞进一个他只想看 2 门的列表里。
> 代价不对称的解法不是"默认开"，而是**候选列表必须全** + **添加时给足判断依据**。

## 7. 提醒

> **现状：数据有了，但语义不是"截止"**。
> 超星给的是章节**开放窗口**（`开放时间：A 至 B`），窗口一关这一章就锁住。
> 所以能做的事是「11/29 就要关了，还差 2 个任务点」，而不是「11/29 前提交」。
> 提醒文案必须用「关闭」这个词，否则在暗示一个不存在的提交动作。

用户原话："有些课程任务点有较早的截止时间……有提醒即将截止的需求"。

只做界面变色不够 —— 他自己说这个 tab 的打开频率**明显低于作业待办**，
看不见的提醒等于没有。

**做法**：复用 `planReminders` 的去重与窗口机制，但不把任务点塞进 task 表。

```ts
// 新增：课程级提醒项（不是 UnifiedTask）
export interface CourseReminderItem {
  key: string;      // `course:${courseId}` —— 必须带前缀，避免与 taskId 撞哈希
  courseId: string;
  title: string;    // 课程名
  detail: string;   // "第3章还剩 2 个任务点"
  dueAt: string;
}
```

- 规则沿用现有 `task-point` 规则（T-3d / T-1d），不新造一套
- 去重键 `makeReminderKey('course:' + courseId, 'task-point:T-3d', dueKey)`，
  写进同一张已发送表 —— 语义一致（同一提醒只发一次）
- 文案：`【3天】任务点：25级数据结构 · 第3章还剩 2 个任务点`

**不做**：任务点没有截止时间时，不提醒、不排期。

## 7.5 刷新节奏（2026-11-04 定）

**不把两个动作合并，但让任务点搭一次便车。**

| | 作业 | 任务点 |
|---|---|---|
| 变化频率 | 分钟级（新发布、改期） | 天级（老师改章节设置） |
| 单次成本 | 一轮同步里的固定份额 | **每门课一个请求**（32 课 = 32+） |
| 触发 | 打开 App / 手动 / 30 分钟内去重 | 进任务点页 + 同步后按天补一次 |

合并的代价：一天开 5–8 次 App → 160–256 个请求/天，超星风控吃不消。
而现在的缺口不是"频率不够"，是**用户不打开任务点页就永远不更新**。

所以：同步结束后**不阻塞地**检查一次（距上次 > 24h 才真抓），
效果就是"每天最多真的抓一次"，用户看到的同步速度不变。
抓完写库，下次进页面看到的就是新的。

不采用"作业同步 N 次后触发任务点"：N 次的时间间隔不可预测
（一天可能同步 8 次，也可能两天不打开）。要的是"每天至少新一次"，
就直接按天判断，别绕道次数 —— 次数只是时间的代理，而且是失真的那种。

并发保护：同一账号同时只跑一份抓取。后台正在抓时用户点「重新读取」，
后者直接返回 `busy`，不会打两份（否则双倍风控暴露）。

## 7.6 截止提醒（v2 · 2026-11-04 待确认，未实现）

### 判据

用户的判断一句话：**提前 24 小时提醒一门视频总时长 30 小时的课，等于通知"你已经来不及了"**。
作业是**时刻**，任务是**工作量**，两者不能套同一套规则。

### 为什么不用精确时长

精确时长拿得到：`GET /ananas/status/{objectid}` → `{"duration":215}`（秒）。
但 objectid 只在**每个章节的详情页**里。一门 15 章 50 个任务点的课要 15+50 个请求。
为一个提前量付这个代价不值，而估错的代价只是"早/晚几小时"，不是"错过"。

### 公式（v2：把日历时间和净投入时间分开）

```
净工作量 W = (总数 - 已完成) × 每个任务点分钟数
日历天数 = W / 每日可投入小时数 D
提前量    = 日历天数 × 24h + 固定冗余
提醒点    = 关闭时刻 - 提前量
```

v1 的错误是 `提前量 = W`，等于假设"收到提醒就连续不间断地刷"。
v2 引入 D，把「要花掉多少小时」换算成「要占用多少天」。

| 参数 | 含义 | 建议默认 |
|---|---|---|
| `minutesPerPoint` | 每个任务点净耗时 | 15 分钟（真机音频 3.6min；文档 10–30；测验 10–20） |
| `dailyHours` (D) | **每天真实能投入的小时数** | **6**（2026-11-04 用户定；设置页可调 2–12） |
| `bufferMs` | 固定冗余（看到提醒→坐下来开始） | 12 小时 |

### D 的张力（需要你拍板）

D 同时控制两件方向相反的事：

| D | 提前量 | 提醒时机 | 隐含假设 |
|---|---|---|---|
| 3h | 长 | 早（可能提前一两周） | 每天只能挤一点，保守 |
| 6h | 中 | 适中 | 课后时间的一半 |
| 10h | 短 | 贴近截止 | 几乎全天在刷 |
| 12h | 更短 | 最贴近 | 除了睡觉都在刷 |

**D 越大 → 提醒越晚 → 越"紧急"**（你说的那个方向），但同时**假设你能突击的强度越高**。
D 定得太大，一旦那几天有课/有考试，提醒就等于没提。

参考量级（W=25h，即还剩 100 个任务点）：

| D | 提前量 |
|---|---|
| 3h | 8.3 天 |
| 6h | 4.2 天 |
| 10h | 2.5 天 |
| 12h | 2.1 天 |

### 三层提醒的分工（这是 v2 的主要结构变化）

| 层 | 触发 | 职责 | 频率 |
|---|---|---|---|
| **一次性弹窗** | 到提醒点 | "该开始了" | 每门课一次 |
| **每日汇总** | 紧急期内，每天那条汇总里带一行 | "还剩几天、还差多少" | 每天 1 条（本来就有的） |
| **页签角标** | 进入紧急期 | "现在还有事" | 常驻，打开就看见 |

第二层正是用户 2026-11-04 提的思路：**不新增通知，把任务点塞进本来就会发的每日汇总**。
好处是不增加打扰次数，坏处是每日汇总必须已经开启（用户关掉了就没有这一层）。

### 每日汇总里长什么样

```
今天有 2 项作业要交
· 高等数学 习题 3.2（23:59 截止）

任务点：形势与政策 还差 3 个（11/11 关闭）
```

措辞刻意**不说"还剩 X 天"** —— 每日汇总是**提前排好**的，正文在排期那一刻就固定了，
到触发时"还剩 3 天"可能已经变成 2 天。这类会漂移的说法只能用"关闭日期"代替
（现有 `buildDailyDigest` 里对远期的作业也是同一套保守处理）。

### 紧急期的定义

`剩余时间 <= 提前量`（即"现在开始、按 D 的节奏，刚好来得及"）。
同一门课在紧急期内：弹窗一次、每日汇总每天一行、角标常亮。

### 已完成 / 已逾期

- 做完了 → 三层全部不出
- 已经来不及（剩余时间 < 净工作量 W）→ 弹窗不排（排了也是"通知你错过"），
  每日汇总和角标照常 —— 那正是"持续提醒"需要覆盖的

### 设置项位置（已定）

**独立一个一级行「任务点提醒」**，不塞进「提醒密度」，也不做二级目录。
理由：设置页的规则是"一级行 = 功能名 + 当前值"，而 D 和"提醒密度"里那套
（作业/考试各提前几小时、提醒几次）不是同一个维度 —— 一个管"提前多久"，
一个管"假设你每天能投入多少"。塞在一起，用户会以为两者共用一套规则。

```
提醒密度      作业 1 天起 · 2 次
任务点提醒    每天 6 小时          ← 新增，与其他项并列
每日汇总      每天 08:00
```

右侧的"每天 6 小时"一眼就能看出它和上面那行不是一回事。

### 每日汇总的开关

沿用现有的 `daily` 总开关：**关掉就不弹，也不会单独为任务点留一条**。

## 8. 请求量账

| 场景 | 请求 | 频率 |
|---|---|---|
| 主同步（作业+考试） | 51（现状，**不变**） | 每次 |
| 添加课程时探测 | N × 1（N≈32） | 极低频，用户点一次 |
| 已添加课程刷新 | M × 1（M 通常 1–3） | 24h 一次 |

净增：稳态 **+1~3 请求/天**。这是它必须独立于 `fetchTasks` 的原因 ——
挂进主同步的话是每次 +32。

## 9. 不做的

- ❌ **单个任务点级别**（"视频《xxx》已看 12/15 分钟"）—— 逐章节请求，成本高且对决策没有增量
- ❌ **代刷 / 自动播放** —— 不碰
- ❌ **章节列表展示** —— 只用来算"最近截止"，不渲染（他的选择是课程级）
- ❌ **每轮同步抓任务点** —— 见 §8
- ❌ **把任务点塞进待办的时间分组** —— 会毁掉「三天内 / 更晚」这套轴

## 10. 取证（已完成）

这个项目为"猜页面结构"付过 5 次返工的代价，这次不猜。需要一份 HAR，包含：

1. 打开一门**有未完成任务点**的课 → 章节列表页（能看到"任务点 6/8"字样）
2. 点进任意一个章节 → 任务点列表
3. 「统计」/「任务点完成情况」页（如果有这个入口）
4. 再给一门**任务点已全部完成**的课做对照（确认完成态长什么样）

要确认的四件事：

| # | 问题 | 为什么非确认不可 |
|---|---|---|
| 1 | 任务点数据是接口 JSON 还是页面 HTML 渲染 | 决定解析器写法（超星作业就是 HTML，考试是 JSON） |
| 2 | 一次请求能否覆盖整门课的任务点 | 决定是 1/课 还是 N/课，直接影响 §8 的账 |
| 3 | 章节级截止时间在不在同一个响应里 | 不在的话，"提醒即将截止"要么放弃、要么多一次请求 |
| 4 | 有没有「计入成绩」标记 | 有的话可以自动筛选，用户就不用手动勾了 |

**阶段 1 的实际取舍（与方案初稿的差异）**：
初稿写"手动勾选决定显示哪些课"，阶段 1 改为**显示所有有任务点的课**（`total > 0`）。
理由：还不知道数字准不准的时候，加一层筛选只会把"抓错了"伪装成"没加这门课"。
等数字可信，再加筛选 —— 顺序反了会掩盖问题。

**阶段 1.5 的取舍**：
- 只显示**还没结束**的窗口。全部过期 = 这门课已经无事可做，留个日期只会让人以为还要赶。
- 全部完成的课**不显示**窗口（"都做完了，11/29 关闭"同样是在制造焦虑）。
- 选**最快关闭**的那个窗口，不是页面上第一个 —— 用户要的是"最近的那个期限"。
- 章节名与窗口是**兄弟节点**，只能靠"往前找最近的 `catalog_sbar`"配对；
  真机上 `chapter_item` 有 19 个而章节只有 15 个，按嵌套切块必然错位，
  而错位是把时间挂到别的章节上，界面上看不出来。
