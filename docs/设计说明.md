# 设计说明 · HomeworkHub

面向要改这个仓库的人。分三部分：架构决策、适配器开发指南、技术难点详解。

---

## 一、架构决策记录

### 1. 为什么核心库不依赖任何 UI 框架

`packages/core` 里没有一行 React / Vue / SwiftUI。原因是这个项目最耗时的部分
（同步、合并、提醒、会话管理）跟「界面长什么样」完全正交，而它们的生命周期完全不同：

- 核心逻辑一年可能要改几十次（平台天天改版）；
- 壳层技术栈可能三年换一次（Tauri → Flutter → 原生）。

所以核心库输出的是一个纯粹的 TypeScript 包，可以被任何壳层内嵌：

| 壳层 | 集成方式 |
| --- | --- |
| Tauri 2（桌面，推荐） | 核心跑在 Rust 侧的 Node 或直接移植到 Rust；前端用 Web |
| Electron | 核心跑在主进程 |
| React Native / Capacitor（移动） | 核心跑在 JS 线程；后台同步用 headless 任务 |
| 纯服务端（自部署） | 核心跑在 Node 服务里，多设备只读同一份数据 |

### 2. 为什么用「端口 - 适配器」而不是 if-else

新增一个平台 = 实现 `PlatformAdapter` 接口 + 在注册表里注册。
引擎、存储、UI 全部零改动。这条约束在写第二个适配器时就开始产生回报了：

- 限流/重试/日志是包在 HTTP 层上的，适配器作者不可能忘记；
- 会话持久化和加密是引擎做的，适配器只负责「产出 Session」；
- 改版检测、防误删、幂等合并是引擎做的，适配器只要老实报错。

对照 WakeUp课程表 的 `CourseAdapter`（继承抽象类 `Parser` 重写 `generateCourseList`），
本项目的契约做了三点改动：数据源无关（不假设输入是 HTML）、
显式声明能力（UI 能提前知道「这个平台需要额外组件」）、会话语义化（支持多账号并存）。

### 3. 为什么先做 JSON 文件存储而不是 SQLite

一个学生一学期大概 200~800 条任务，序列化不到 1 MB。这个量级下
「整文件读入 + 原子写回」完全够用，而且零依赖、可直接被任何宿主读取、出问题能直接看。

超过约 1 万条再换 SQLite —— 那时只需实现同一个 `HubStore` 接口，引擎零改动。

### 4. 为什么错误要分类

同步引擎必须能区分「要我重新登录」和「平台挂了」：

| 错误码 | 是否重试 | 是否打断用户 | UI 该做什么 |
| --- | --- | --- | --- |
| `AUTH_REQUIRED` | 否 | 是 | 弹登录框 |
| `CAPTCHA_REQUIRED` | 否 | 是 | 提示改用粘贴 Cookie |
| `RATE_LIMITED` | 是 | 否 | 静默退避 |
| `NETWORK` / `UPSTREAM` | 是 | 否 | 静默重试 |
| `SCHEMA_DRIFT` | 否 | 是 | 提示「平台改版，请更新适配器」 |
| `SIGNER_UNAVAILABLE` | 否 | 是 | 提示缺组件；降级为只读 |

如果只有一个 `Error` 类型，UI 层就只能显示「同步失败」——用户既不知道
该做什么，也不知道数据还安不安全。

## 二、适配器开发指南

### 最小实现清单

新建 `packages/adapters/<平台>/src/index.ts`，实现 `PlatformAdapter`：

```ts
export class MyAdapter implements PlatformAdapter {
  readonly id = 'myplatform';
  readonly displayName = '某平台';
  readonly homepage = 'https://example.edu.cn';

  // 1. 诚实地声明能力。这决定了 UI 怎么呈现、引擎怎么调度。
  readonly capabilities: AdapterCapabilities = {
    courses: true,
    tasks: true,
    exams: false,
    incremental: false,        // 接口没有增量语义就老实写 false
    cookieOnlySession: true,
    requiresNativeSigner: false,
    aggressiveAntiBot: false,
  };

  readonly authMethods: AuthMethod[] = [
    { id: 'password', label: '账号密码', kind: 'password',
      fields: [{ key: 'username', label: '账号' },
               { key: 'password', label: '密码', secret: true }] },
  ];

  // 2. 声明你允许发出的非 GET 请求。
  //    这份清单是整个 app「会发出哪些写请求」的完整审计材料，通常只有 1~3 行。
  readonly readOnlyPolicy: ReadOnlyPolicy = {
    allowMethods: ['GET', 'HEAD'],
    allowPost: [
      { pattern: /\/login$/, why: '账号密码登录' },
      { pattern: /\/api\/work\/list$/, why: '查询作业列表（只读）' },
    ],
  };

  // 3. 登录：只负责产出 Session，不要自己管持久化。
  //    用户粘贴凭证的路径必须标 origin: 'imported'。
  async login(ctx: AdapterContext, cred: Credentials): Promise<Session> { /* ... */ }

  // 4. 会话探测：必须用最便宜的接口，绝不能为了探测去拉全量作业
  async probeSession(ctx: AdapterContext, s: Session): Promise<boolean> { /* ... */ }

  // 5. 课程 + 任务：产出「半成品」，交给 engine 补主键/指纹/revision
  async fetchCourses(ctx, s, req?): Promise<Page<PlatformCourse>> { /* ... */ }
  async fetchTasks(ctx, s, req): Promise<Page<PlatformTask>> { /* ... */ }

  // 6. 可选：构造深链，让用户能一键跳到平台页面
  buildTaskUrl?(courseId: string, task: PlatformTask): string | undefined;
}
```

### 四条硬性要求

**① 用 `SessionHttpClient` 发请求，不要直接调 `ctx.http`。**

它负责「带 cookie → 收 Set-Cookie → 合并回会话」。
自己写必然有人漏掉合并那一步，表现为「登录成功但第二次请求就 401」，
极难排查。顺带它还统一处理了 401/403、被风控拦到登录页等情况。

```ts
const http = new SessionHttpClient(ctx, session);
const res = await http.postForm<TaskListResp>(url, { courseId, ut: 's' });
```

**② 解析失败必须抛 `schemaDrift`，绝不返回空数组。**

这是本类应用最严重的故障模式：平台改版后解析出 0 条，
从代码角度「成功」了，从用户角度是「我作业不见了」。
所以：

```ts
if (!Array.isArray(body.list)) {
  throw schemaDrift(this.id, `预期字段 list 为数组，实际为 ${typeof body.list}`);
}
// 上游声明有 N 条但解析出 0 条，同样是改版信号
if (items.length === 0 && (declaredTotal ?? 0) > 0) {
  throw schemaDrift(this.id, `上游声明 ${declaredTotal} 条，实际解析出 0 条`);
}
```

**③ 不要为了「看起来快」而并发请求。**

限流器是按平台全局共享的，并发只会让请求排队，却显著提高触发风控的概率。
超星这种强风控平台必须顺序请求。

**④ 只读，而且只读得克制。**

守卫会拦住显式的写操作，但它拦不住「你在适配器里写了会打点的接口」。
判断标准不是「接口名听起来像查询」，而是：**这个请求会不会在服务端留下痕迹？**
进入课程页会记学习时长、拉取题目会写「已开始答题」、打开通知会写已读回执 ——
这些都属于要避免的。新增任何非 GET 请求时，先问一遍这个问题。

### 用 Mock 平台验证你的适配器

`packages/adapters/mock/src/server.ts` 是一个会「使坏」的假平台，
可以注入 429 / 5xx / 会话失效 / 字段改名 / 任务增删改。
把它的响应格式挪到你的平台形态，就能在拿到真实账号之前
把适配器的错误处理路径全部跑一遍。

```ts
platform.setMode('drift');        // 模拟平台改版
platform.setMode('ratelimit', 1); // 模拟限流
platform.invalidateSessions();    // 模拟会话失效
platform.shiftDeadline('id', ...) // 模拟老师改期
platform.deleteTask('id');        // 模拟任务被删
```

## 三、技术难点详解

### 难点 0 · 「不影响平台正常使用」怎么变成强制约束

这是本项目的第一条设计前提，不是附录。它由三层机制共同保证。

**① 只读守卫：`engine/read-only-guard.ts`**

包在传输管道最外层（守卫 → 限流/重试 → 真实传输），
适配器无法绕过。三条规则：

```
Rule 1  方法白名单：默认只允许 GET / HEAD
Rule 2  显式放行：任何非安全方法必须在适配器的 readOnlyPolicy.allowPost
        里逐条声明并写明用途
Rule 3  兜底黑名单：命中即拒绝，优先级高于白名单
```

Rule 3 的执行顺序刻意排在 Rule 2 **之前**：即使有人误把提交类路径写进白名单，
也拦得下来。一处配置失误不应该能破坏整个承诺。

`DEFAULT_FORBIDDEN_PATTERNS` 里包含了一些容易被忽视的路径：

```ts
/(mark-?read|markread|read-?receipt)/   // 已读回执 —— 会改变通知状态
/(study-?record|watch-?log|heartbeat)/  // 学习时长上报 —— 会污染学习行为数据
/\/(logout|signout)/                    // 退出登录 —— 会把用户自己的会话也干掉
```

这三类都不是「作弊」，但都会在用户不知情的情况下改变他在平台上的状态。
最后一条尤其要注意：一旦调用，用户自己也会被登出。

另外还拦 URL 参数里的动作（`?action=submit`），因为很多平台把动作放 query 里。

**② 会话来源策略：`ports/vault.ts` 的 `SessionOrigin`**

```
imported  用户自己从浏览器/客户端复制出来的会话
          我们只是旁观者，**永远不用账号密码去重新登录**
derived   我们用账号密码独立登录取的会话
```

为什么 `imported` 必须禁止自动续期：**重新登录 = 在服务端创建新会话**。
多数平台是单点登录或会轮换 token，那会把用户正在用的那个客户端顶下线。
这是「影响正常使用」最典型的一种表现，而且用户根本不会想到是我们的锅。

引擎自始至终不保存明文密码，所以在物理上就没有自动续期的能力。
但这条注释仍然写在 `#ensureSession()` 上，因为**将来如果有人想在这里加自动续期，
必须先读那段话**。

提示语由 `#authMessage()` 统一附加，而不是在各个发现会话失效的地方各写一遍 ——
会话失效可能在过期探测、拉课程、拉任务三处被发现，
不集中处理就会出现「有时候说得很清楚，有时候只丢一句 401」。

**③ 风控友好节奏**

每平台一个全局共享令牌桶（多账号共用配额）、课程列表 12h TTL 缓存、
429 的 `Retry-After` 回灌限流器、全抖动指数退避、401/403 不重试。

**可验证性**

`demo` 场景 14 专门验证这条承诺，并且 mock 服务器里放了一个
`POST /submit` 诱饵：测试主动去尝试提交，然后断言被拦下、且服务端记录中
该请求从未出现。「从没被尝试过的保护措施等于没有保护措施」。

对应的单元测试在 `describe('只读守卫')` 与 `describe('会话来源策略')` 里。

**边界（必须对用户交代）**

无法 100% 保证零影响（风控是黑盒）；会话失效是必然的（这是设计不是缺陷）；
不应与官方客户端同时高频使用（部分学校禁止账号共享）。

### 难点 0.5 · 把「零影响」走到底：换载体而不是换适配器

只读守卫解决的是「不发写请求」，会话来源策略解决的是「不新建会话」。
但共享会话的路线仍然要向平台发读请求。再往下还有两级，
关键设计洞察是：**把传输层做成 `HttpClient` 的替身，任何适配器零改动就能换载体。**

```
引擎 → 只读守卫 → 限流重试 → [HttpClient 替身] → 平台
                                ↑ 换这里就行
```

#### 路线 A · HAR 录制与回放（`infra/recording-http.ts` + `infra/har-replay-http.ts`）

`RecordingHttpClient` 包在真实传输外面，一轮同步就把响应固化成标准 HAR；
`HarReplayHttpClient` 则是一个**一个真实请求都不发**的传输 ——
适配器照常「请求」接口，拿到的是上次抓包的响应。

三个用途：
1. **首次导入**：用户在浏览器正常操作一次 → DevTools 导出 HAR → 拖进来。
   我们从头到尾没碰过他的登录态，连一个 GET 都没有。
2. **适配器离线开发**：把真实响应固化下来反复调解析器。
   这比「拿真实账号反复试」安全得多 —— 后者才是最容易触发风控的行为。
3. **改版回归测试**：新旧 HAR 对比，立刻知道哪几个接口变了。

两个实现细节值得记：

- **匹配两级策略**：先按「方法 + 完整 URL（含 query）」精确匹配；
  失败再按「方法 + 路径」兜底，且优先取还没被消费的那条 ——
  真实抓包里 query 经常带时间戳/csrf，只按精确匹配会大量漏配。
- **默认跳过非 2xx 的录制条目**：录制时本来就失败的请求（登录页、验证码页）
  回放它只会让适配器误判成改版。

⚠️ **脱敏是默认且不可关闭的**。HAR 里天然包含 Cookie 与 Authorization，
那是完整登录凭证，留在文件里等于把账号密码写进一个会被随手转发的 JSON。
回放只需要响应体，凭证毫无用处 —— 所以 `RecordingHttpClient` 强制剥掉，
并提供 `containsSensitiveHeaders()` 供测试断言。

局限：回放是快照，不是持续同步。老师今天新布置的作业它看不到。

#### 路线 B · CDP 附着（`infra/cdp-http.ts`）

借用户**已经登录**的浏览器发请求：
`引擎 → 守卫 → 限流 → [CdpHttpClient] → WebSocket → 浏览器标签页 → 平台`。

- 不创建任何新会话（不会有「新设备登录」提示）
- **凭据不过手**：cookie 由浏览器自动附带，而 HttpOnly cookie 对页面 JS 不可见 ——
  我们连读都读不到，更不可能存
- 身份 100% 是用户本人，频率由我们控制

这是 iSmart 这类「客户端是套壳 Chromium」的平台唯一现实的只读路径。
社区的 iSmartAuto 就是这么发现客户端可以加 `--remote-debugging-port` 的；
区别在于他们用它提交答案，我们只用它读取作业。

两个必须想清楚的坑：

1. **CORS**。请求在页面上下文里 fetch，跨源会被浏览器拦掉，
   而 fetch 的 CORS 失败会静默返回空 —— 正是本项目最忌讳的「静默返回空」。
   对策：`pickTargetForOrigin()` 按请求的 origin 自动挑标签页，
   挑不到就显式报错并告诉用户该打开哪个页面。
2. **HttpOnly 是优点也是边界**：好处是凭据不过手；
   边界是「登录态是否有效」只能靠响应状态码判断，不能靠读 cookie 过期时间。

报文层抽成了纯函数（`buildPageFetchExpression` / `parseCdpFrame` / `pickTargetForOrigin`），
WebSocket 通过 `WsFactory` 注入 —— 所以不需要真的开一个 Chrome 也能完整单测
（包括「恶意 URL 不能逃逸出字符串」的注入防护）。

#### 一个踩出来的坑：离线路径必须显式圈定范围

`import-har` 最初实现时调的是 `syncAll()`（不带参数），
结果引擎把库里**所有账号**都同步了一遍 —— 包括挂着真实会话的账号，
「零网络请求」的承诺被一行代码悄悄破坏了。

所以两条离线命令都强制传 `accountIds: [account.id]`。
**默认行为是全局的，而全局行为对离线场景是危险的。**

### 难点 1 · 截止时间归一化（最脏的一层）

各平台对「什么时候截止」的表达方式完全不同：

| 平台 | 原始形态 |
| --- | --- |
| 超星 | `2026-09-25 23:59`（本地墙上时间字符串） |
| 雨课堂 | `endTime: 1758815940000`（epoch 毫秒） |
| 雨课堂（部分） | `'还剩 3 天'`（倒计时） |
| iSmart | 剩余秒数（纯数字） |
| 教务系统 | `第 4 周 周五 第 3-4 节`（需要学期日历换算） |
| 各种 | `未公布` / `不限时` / 空字符串 |

不在这里归一化，后面每一层都要写 if-else，最终必然漏掉某个平台。
`normalizeDeadline()` 把输入压成四态：

```
absolute  明确时刻
relative  剩余时长（value + unit）
open      显式无期限
unknown   看不懂 —— 保留 raw 原文，绝不静默丢弃
```

**踩过的坑（值得单独说）：**

1. **时区。** 早期用 `Date.UTC()` 解析 `2026-09-25 23:59`，
   结果 UTC+8 用户整体偏移 8 小时。平台给的是用户所在时区的墙上时间，
   必须用本地时间构造。

2. **相对时间的锚定。** 平台说「还剩 3 天」，如果每次同步都按
   「当前时刻 + 3 天」重新解释，这个任务**永远到不了期** ——
   第五天看它还是「还剩 3 天」，提醒永远不触发，排序永远是最后。

   修法：首次观测时锚定成绝对时刻（`UnifiedTask.deadlineAt`），之后一直沿用。
   并且只在倒计时**变大**（真改期）时才重新锚定；
   变小只是时间自然流逝，不算变更（否则每天同步都会产生一次假的「截止时间已变更」）。

3. **时间精度。** 平台返回的时间戳精度不一致（有的到秒、有的到毫秒），
   直接比较会把每一轮同步都判定成「截止时间变了」，于是 revision 无限增长、
   提醒被反复重置。所以比较前先按 1 分钟粒度对齐。

### 难点 2 · 幂等合并

一次同步拿到几百条任务，重复跑不能产生重复记录，也不能产生无意义的写操作。
`mergeTasks()` 是个纯函数（无 IO、无网络、无时钟），所以能完整单元测试。

**主键两级策略：**

```
1. platformTaskId —— 平台给了就用，稳定且免费
2. fingerprint   —— sha1(平台, 课程, 类型, 归一化标题)
```

标题归一化必须剥离「（第2次）」「[已修改]」这类老师手动加的噪音后缀，
否则同一份作业会重复入库。但指纹**不能**包含状态和截止时间 ——
交作业、改期都应该表现为「变更」，而不是「新建一条」。

**主键必须包含账号维度（踩过的坑）。**
`platformId + hash(accountId) + platformTaskId`，缺了账号会让
同一平台的两个账号（比如两个学校的学习通）的 `work_88001` 互相覆盖。
账号段用哈希而不是明文，因为主键会出现在 URL、日志和 UI 里。

**防误删（踩过的坑）：**
分页请求失败、临时风控、接口超时，都会让某一轮同步「少看到」一些任务。
立刻删库会让用户看到作业一闪一闪。所以：

- 连续缺席 N 轮（默认 2）才软删除，且只软删除不硬删（可能被上游恢复）；
- 数据不完整（翻页中断 / 达到翻页上限 / 演练模式）时，**整轮禁用删除判定**。

### 难点 3 · 提醒的去重与补发风暴

- **幂等：** 同步每 30 分钟跑一次，如果只按「是否进入 24 小时窗口」判断，
  用户一天会被提醒 48 次。所以每个提醒有唯一 key = `sha1(任务, 规则+窗口, 截止时间)`，
  发过就记档。
- **改期：** 截止时间编进了 key，改期后 key 自然不同，不需要额外的重置逻辑。
- **补发风暴：** 一个作业昨晚发的、今晚截止，用户今天才第一次同步，
  此时 T-7d/T-1d/T-3h 三个窗口全都「已满足」。逐个补发会瞬间刷出三条重复通知。
  所以每轮每任务**最多只发最紧的那一条**，并把更宽松的窗口一起标记为已消费。
- **逾期宽限：** 逾期超过 3 天的任务不再提醒，防止老任务刷屏。

### 难点 4 · Native 签名（iSmart 的 `ut` 字段）

iSmart 把签名逻辑编译进了原生 so/dll，纯 JS 拿不到，签名不对后端就不认。
这是**无法用 TypeScript 解决**的问题，硬做只会把整个项目锁死在某个平台。

架构对策是把签名抽成可替换的端口 `NativeSigner`：

- `SubprocessSigner` —— 通过 stdin/stdout 的 JSON 协议调用外部可执行文件。
  选进程边界而不是静态链接，是为了崩溃隔离（unidbg 跑在 JVM 里，内存占用大）
  和许可清晰（签名组件常是 GPL 或来源不明的二进制）。
- `UnavailableSigner` —— 没有签名能力时**显式失败**，绝不返回假签名。

于是没有签名组件的用户**降级为「只读提醒」模式**：仍能看到作业和截止时间，
只是不能自动拉取或提交。这个降级比「要么全能要么不能用」友好得多。

### 难点 5 · HTTP 层的两个隐蔽细节

**① 必须手动跟随重定向。**
Node fetch 自动跟随重定向时，中间跳转收到的 `Set-Cookie` 会被丢掉。
而超星/雨课堂的登录链路恰恰是「POST 登录 → 302 到主页 → 主页下发会话 cookie」。
自动跟随会拿到一个「登录成功但没有会话」的诡异状态。

**② 限流不能只在适配器层做。**
429 时把 `Retry-After` 回灌给限流器（而不是只 sleep 这一次），
后续请求自动降速；退避用全抖动指数退避，避免多个账号在同一时刻齐步重试形成新尖峰。
另外 401/403 不该重试 —— 重试也不会变好，只会浪费请求额度、加剧风控。
