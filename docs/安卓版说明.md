## 一、构建与安装

```bash
cd homework-hub
npm install                 # 只为拿 typescript
npm run android:apk         # 生成前端资源 + 打 APK
```

产物：`release/homework-hub-0.1.0-debug.apk`（约 550 KB）

安装（任选一种）：

```bash
# USB 调试已打开
adb install -r release/homework-hub-0.1.0-debug.apk
```

或者把 APK 传到手机上点击安装（需允许「安装未知来源应用」）。

也可以用 Android Studio 打开 `android/` 目录，然后直接点 Run。
（首次打开时 Studio 会按 `gradle/wrapper/gradle-wrapper.properties` 下载 Gradle 8.7。）

**已验证的环境**：JDK 17 + Gradle 8.7 + AGP 8.5.2 + compileSdk 34 + build-tools 34.0.0。
这台机器上 `gradle assembleDebug` 通过，产物 552 KB。

## 二、架构：为什么手机上要这么绕

```
WebView（我们的引擎，编译成 ESM）
  └── fetch('/api/...') → 被 main.js 拦截 → 引擎 → HttpBridge（原生） → 平台
```

三个必须解决的约束：

| 约束 | 解法 |
| --- | --- |
| WebView 里没有 `node:fs` / `node:crypto` | `PersistentStore`（localStorage）+ `WebCryptoVault`（AES-256-GCM，算法不变） |
| 页面的 `fetch` 受 CORS 限制，平台不会给我们 CORS 头 | 所有平台请求走**原生 HTTP 桥**（HttpURLConnection 不受 CORS 约束） |
| `file://` 下 ES Module 会被 CORS 拦掉 | 用 `WebViewAssetLoader` 把 assets 挂在 `https://appassets.androidplatform.net` |

**同一个 API 实现跑在两处**：桌面走 HTTP（`apps/web/src/server.ts`），
手机走进程内拦截（`apps/android/www/main.ts`），两者共用 `apps/web/src/api.ts`。
前端 UI（`apps/web/public/app.js`）一行不改 —— 所以桌面端验证过的界面逻辑，
在手机上是同一份。

## 三、登录方式（这是关键差异）

手机端**主推「在应用内登录平台」**，而不是让用户粘贴 cookie：

1. 点右上「登录平台」→ 选平台 → 应用内的 WebView 打开平台官网
2. 你在官方页面上正常登录（扫码、密码都行 —— 那是平台自己的页面）
3. 登录完成、页面自动跳转回应用界面时，应用立刻登记账号并读取一次

为什么这样最安全：

- **凭据不过手** —— 密码只出现在平台的官方页面里，我们不接触
- **Cookie 不进入 JS** —— 它待在 Android 的 `CookieManager` 里，
  我们的 JS 从头到尾读不到（HttpOnly cookie 对页面脚本本来就不可见）
- **不新建会话** —— 用的是你自己在官方页面登录出来的那个会话，不会把别的设备顶下线

其他方式也都保留：粘贴 Cookie（离线登记，零请求）、HAR 回放（零网络）、
账号密码（走适配器的 login，会创建新会话 —— 最不推荐）。

## 五、排查：出问题看这里

### 先看日志

```bash
adb logcat -s HomeworkHub:V
```

页面的日志也会打到这里（引擎通过 `Android.log()` 上报）。
想看更细的，把引擎日志级别调高：在 `main.ts` 里把 `new ConsoleLogger({ level: 'info' })`
改成 `'debug'` 后重新 `npm run android:apk`。

### 白屏 / 一直转圈

按可能性排序：

1. **前端资源没打进去**。检查 APK：
   ```bash
   unzip -l release/homework-hub-0.1.0-debug.apk | grep -c "assets/www"
   # 应该输出 45
   ```
   如果是 0，说明忘了先跑 `npm run android:sync`。

2. **模块加载失败**（说明符改写或 node: 引用残留）。构建脚本本应拦住：
   ```bash
   npm run android:sync   # 会做 node: 扫描 + 导入目标存在性校验
   ```
   输出里三行都必须通过：`node: 引用扫描`、`import 目标校验`、`已改写说明符`。

3. **WebView 版本太老**。需要 Android 8.0+（minSdk 26）且 WebView 支持 ES Module。

### 同步报「没有原生 HTTP 桥」

说明 JS 与原生之间的桥没接上。检查：

- 是不是在电脑浏览器里打开了 `index.html`？那本来就没有桥，请用 `apps/web/src/server.ts`
- `adb logcat` 里搜 `AndroidBridge` 有没有异常

### 同步报 401 / 需要重新登录

在「账号」页重新点一次「打开 XX 登录」，登录完会自动重新读取。

### 某些平台一直失败

**这是最可能的情况，也是最需要你反馈的。** 请把下面这些发给我：

1. `adb logcat -s HomeworkHub:V` 里同步那一段的完整输出
2. 应用里显示的失败原因原文（会包含是哪个接口、返回了什么结构）
3. 如果能抓到 HAR 更好：在电脑浏览器登录该平台、打开作业页面、
   DevTools → Network → 右键「Save all as HAR with content」→ 把文件发我
   （导出时已自动脱敏，不含 cookie）

有了真实响应，我就能离线把解析器对准 —— 不需要你的账号密码。

## 七、0.1.1 更新（2026-09-25，针对第一轮真机反馈）

### 学习通「新增 0」的根因与修复

上一版适配器把作业列表接口按 **JSON** 解析，但社区验证的真实行为是：

- 课程列表：`mooc1-api.chaoxing.com/mycourse/backclazzdata?view=json&rss=1`（JSON，含 cpi）
- 作业列表：`mooc1-api.chaoxing.com/work/task-list?courseId=&classId=&cpi=`（**HTML**：
  `<li>` 里是「未交/已交」状态 + `<p>` 标题 + `<span class="fr">剩余X小时Y分钟</span>`）

0.1.1 已改为按真实格式解析，旧的 JSON 接口保留为回退。同时加了**全空诊断**：
如果所有课程都解析出 0 条任务，同步会明确报错并列出每门课的抓取结果——
「新增 0」这种静默假成功不会再出现（要么有数据，要么给出可上报的错误）。

### 一键同步（自动重登）

- 账号密码登录时默认**记住密码**（AES-256-GCM 加密存放，与会话同级保护；可勾掉）
- 会话失效时引擎自动重新登录并重拉作业 —— 点一下同步，从登录到入库全流程跑完
- 粘贴 cookie / HAR / CDP 路线**没有**这个行为：没有密码，绝不会替你登录
- 账号列表会显示「🔑 一键重登」徽标表示该账号已记住密码

### 注意

- 「在应用内登录平台」（WebView 官网页登录）仍然不存密码 —— cookie 由系统
  CookieManager 保管，失效后需要重新点一次登录，这是它的安全设计
- 倒计时形态的截止时间（剩余X小时）按同步时刻推算，存在分钟级误差；
  同步越频繁越准

## 八、0.1.2 更新（2026-09-27，真机反馈：WebView 线程崩溃）

**现象**：同步报「课程列表拉取失败：A WebView method was called on thread
'pool-2-thread-3'. All WebView methods must be called on the same thread」。

**根因**：原生 HTTP 桥的请求跑在工作线程上，但每次请求都在那个线程里调
`webView.getSettings().getUserAgentString()` 取 UA —— Android 强制要求
WebView 方法只能在主线程调用，于是**每一个**原生请求都直接抛异常。
这也解释了为什么作业接口从来没真正发出去过。

**修复**：UA 在 HttpBridge 构造时（主线程）一次性取好缓存，工作线程只读字段。
全桥已复查，其余跨线程调用都走了 runOnUiThread。

**升级方式**：覆盖安装 0.1.2。之前登记的账号数据不受影响。

## 三十四、0.1.28 更新（2026-10-04，Invalid string length 收网）

真机：三个平台抓取全部成功（超星 84 条、iSmart 6 条、长江 9 条 ✅），

本轮四处收网，每一处都是「把可能产生超大字符串的路径堵死」：

1. **localStorage 快照最小化**（最可疑的一处）：以前把**整个 localStorage**
   序列化后传给应用（平台网页会往 localStorage 塞大量缓存，可能几 MB），

3. **保险箱 base64 改分块**：逐字节 `s += String.fromCharCode(b)` 在数据量大时是

1. **移除 = 留下墓碑**：移除账号时记下「用户否决过这个身份」。之后从平台页返回时
   **不再静默重建**，而是问一次：「这个账号此前已被你移除，是否重新添加？」
   确认后才重建；取消则保持移除状态。
2. **账号密码登录视为显式意图** → 直接撤掉墓碑（你在表单里填了，就是明确要加）。
3. **移除时连游标一起清**（`course-exclude` / `course-crawl` / `full-diagnostics`）。
   此前残留的游标会被重建的账号「继承」—— 表现为新账号莫名其妙跳过某些课。
4. **移除立即落盘**（不等 400ms 去抖）：破坏性操作不能有「点了但没存」的窗口。
5. **账号名可辨识**：应用内登录的账号从 `browser` 改为「超星学习通（应用内登录）」
   —— 同一个平台的多个账号一眼能分清。

## 三十七、0.1.31 更新（2026-10-06，超星「一条都不留」的真正原因）

你指出得对：**静默合并不会让一个平台一条都不剩**（每条指纹至少留下一条）。
所以除了合并，还有第二个原因。查到了：

### 根因：期限未知的任务被整体丢弃（前后端不一致）

`upcoming()` 里原本有这么一句：

```js
// 无期限任务不过滤掉，但不参与最近截止排序
return t.deadline.kind !== 'unknown';
```

写「不过滤掉」的注释，行为却是**直接丢弃**。后果是这类任务**两个视图都进不去**：

- **待办**：在这里被丢弃；
- **已完成**：它只收「已提交/已批阅/已过期」，而这类任务状态不是终态。

于是任务**在库里，却在界面上彻底不可见**。前端 `renderTodo` 其实早就准备了
「期限未知」分组（order 里有 `unknown`）—— 是后端先把它们滤掉了，前后端不一致。

超星的 84 条如果截止时间全都没解析出来（`parseTaskListHtml` 的日期正则
要求「4 位年-月-日」，页面格式一变就整批失配），就会**全部不可见** ——
这正是「整个平台不管待办还是已完成都没有」。

**修复**：期限未知的任务**保留并显示**，归入「期限未知」分组。

### 同时新增「数据体检」行

待办页底部现在会在「库里的条数多于界面上看得见的」时显示一行，例如：

> 库中 91 条 · 当前可见 4 条（80 条被你删除、7 条无截止时间）
> chaoxing 0/84 · ismart 1/3 · yuketang-changjiang 3/4

这是为了不再靠猜 —— 真机已经出现两次「数据在库里但界面看不到」，
两次都只能靠推理。有了这行，任何人一眼就能看出**差额是多少、差在哪、按平台怎么分布**。

> 装 0.1.31 后同步一次。如果超星的任务出现了，就是上面的原因；
> 如果仍未出现，体检行会直接告诉我们真实原因（比如「84 条被你删除」）。

## 三十八、0.1.32 更新（2026-10-06，持久化改用原生文件存储）

你补充的完整描述把问题定死了：**「同步后显示正常，清除后台重进就丢超星」**
—— 数据在库里、界面也能渲染，丢的是**落盘**这一步；而且只丢一个平台，
说明丢的是**最后写入的那一批**。

### 根因：WebView 的 localStorage 不保证及时刷盘

localStorage 的写入是「先写内存、由浏览器引擎择机刷盘」。
App 被从最近任务里划掉时进程直接被杀（**拿不到正常的 onPause 时机**），
未刷盘的那部分数据就随进程一起消失了。同步里最后写入的平台（超星那 84 条）
正好是这一批 —— 所以表现成「只丢超星，而且丢得干干净净」。

这也解释了为什么它看起来像「整个平台凭空消失」而不是「少了几条」。

### 修复：状态存到原生文件（写成功即落盘）

- 新增原生键值存储：**同步写临时文件 → `fsync` 强制刷盘 → 原子重命名**。
  `fsync` 是关键，少了它数据可能还在页缓存里，等于没解决；
  先写临时文件再改名，保证写一半被杀也不会毁掉旧数据。
- 引擎状态（`hh.state.v1`）与保险箱（`hh.masterkey.v1` / `hh.session.*`）
  都走这条通道，彻底不依赖 localStorage 的刷盘时机，也没有 5MB 配额限制。
- **老数据自动迁移**：首次启动时把 localStorage 里的 `hh*` 键搬到文件存储
  （只搬原生侧还没有的键，不覆盖新数据）—— 你现有的账号与作业不会丢。

### 附带：存储健康度可见

- **落盘失败会直接弹提示**：「数据保存失败：…。重启后最近同步的数据可能丢失。」
  以前它只写 console，真机上根本看不到 —— 这正是这个 bug 拖了这么久的原因。
- 待办页的体检行会显示「存储约 N KB」；只要出现过写入失败，
  它会持续显示失败原因。

> 装 0.1.32 后：同步一次 → 清除后台重进 → 超星的数据应该还在。
> 如果仍然丢，体检行会直接显示写入失败的原因。

## 三十九、0.1.33 更新（2026-10-06，同步提速 + 静默同步）

你的两个方向分开处理了 —— 结论是：**「提速」的空间比想象小，而「体感」的空间比想象大**。

### 先说诊断（用你自己的遥测数据）

| 平台 | 限流 | 请求数 | 耗时 |
|---|---|---|---|
| 长江雨课堂 | 5 rps | 1~4 | 0.2~1s |
| iSmart | 1 rps | 4 | ~1s |
| **超星** | **4 rps** | **~80** | **~20s** |

超星那 20 秒不是程序慢，是 **请求数 ÷ 速率** 的数学结果。你要求「尽可能减少触发风控」，
那速率就不能提 —— **提速的唯一出路是减少请求数**。而超星的 80 个请求里，
**每门课固定发一次考试请求，占约 40%**。

### 1. 考试请求按课程活跃度分级（自动）

给每门课算「活跃度」，判定从严（宁可多查一次，也不漏老师临时发的小测验）：

| 课程状态 | 作业请求 | 考试请求 |
|---|---|---|
| 活跃（有未完成任务 / 近 14 天有变化） | 照查 | **照查** |
| 静默（全部任务终态 **且** 14 天无变化 **且** 库里已有数据） | 照查 | **跳过** |

新测验只会出现在活跃课程里，所以**不会漏**；而往期课程的考试时间窗早已关闭。
按你 32 门课的情况，请求数可从 ~80 降到 ~30，**耗时 20s → 8s 左右**。

### 2. 课程同步设置（手动，你加的那个设计）

账号页新增「课程同步设置」：列出每个账号下的课程，取消勾选即让该门课**不再同步**。

- 与「删整课」的区别很重要：**删整课会连记录一起删掉，静默只停止请求 —— 已有记录完整保留**；
- 往期课程就该用这个：省掉全部请求，历史记录仍然能查；
- 静默是长期偏好，**重新登录不会自动撤销**（与删整课被登录清除的语义相反）。

### 3. 静默同步：把时间挪到看不见的地方

**没有做真正的后台同步**，因为架构上做不到：同步引擎跑在 WebView 的 JS 里，
App 切后台后 JS 定时器被系统节流到每分钟最多一次，被划掉更会直接中断进程。
真后台只能靠常驻通知栏的前台服务，或把引擎重写成原生 —— 都不划算。

**改成等价的方案**（stale-while-revalidate）：

- 打开 App / 切回前台 → **立刻显示已有数据**（0 等待）→ 自动静默同步 → 数据自己变新；
- 同步过程**不再弹全屏遮罩**（以前那句 `busy(syncing)` 会把界面锁住），只在标题栏显示「正在更新…」，你照常滑列表；
- **30 分钟限频**（按你的决定）：距上次同步不足 30 分钟就跳过；**手动点同步 = 强制**；
- 只在手机端自动（电脑端是开发环境，不该自动刷平台接口）。

**静默同步可以安静地成功，但绝不安静地失败** —— 有账号失败时仍然会弹提示。

### 安全边界（都有测试守着）

这两个机制都会「主动不去看某些数据」，最大的风险是把**没看的东西误判成消失并删掉**：

- 静默课程的考试任务**排除出删除判定**（否则连续缺席会被软删除）；
- 被静默/跳过课程的存量数据一律保留，且不标记删除；
- 课程里有任何未完成任务 → **永不判静默**。

> 装 0.1.33 后：打开 App 不用点同步也会自己更新；到账号页 →「查看课程列表」，
> 把往期课程取消勾选，下一次同步应该明显变快（日志页能看到请求数下降）。

## 四十二、0.1.36 更新（2026-10-07，同步统一为非阻塞 + 常驻状态条）

### 问题

同一个「同步」动作，不同入口的体验不一致：

- 自动同步（打开 App / 切回前台）→ 不挡界面；
- **手动点同步、账号失效重登后触发的同步 → 全屏遮罩，把界面锁住十几二十秒**。

用户只能靠「这次有没有被挡住」来猜是谁在同步，而且被挡住时既看不了已有待办、
也做不了别的事 —— 而他其实只需要知道「它在跑」。

### 改动

**所有同步入口统一为非阻塞**，改用底部的**常驻状态条**：

| 状态 | 显示 |
|---|---|
| 运行中 | `⟳ 正在同步… 12 秒`（带计时，看得出没卡住） |
| 成功 | `✓ 同步完成 · 3 个账号 · 新增 2 · 更新 1`（3.5 秒后自动收起） |
| 失败 | `⚠ 同步 3 个账号：2 成功 · 1 失败（超星）—— 详情见日志`（保留 9 秒） |

- 状态条**不拦截点击**（`pointer-events: none`），同步期间可以照常翻列表、切 tab；
- 「账号失效 → 用保存的密码自动重登 → 重试」这条链路也在 `/api/sync` 内部，
  现在同样只体现在状态条上；
- 「在应用内登录平台后返回」触发的同步也统一了（它以前有自己的遮罩）；
- **防重入**：重复触发（比如自动同步撞上手动同步）不会叠起两次同步；
- 与后端状态对齐：别处触发的同步（原生侧调 `syncNow`）也会显示进度，
  结束后自动收起。

**保留全屏遮罩的**只限于「用户主动发起、必须等他做完」的短操作：

## 四十四、0.1.38 更新（2026-10-08，手动添加待办 + 截止提醒进通知栏）

### 1. 手动添加待办

待办页底部新增「＋ 添加一条」：**作业名称 / 截止时间 / 课程名称 / 平台名称**，
四个字段全部自己填（没有下拉，也不限已知平台）。

为什么不做成选择框：不是所有作业都能从平台抓到 —— 老师口头布置的、别的网站的、
平台接口没覆盖的。把平台做成下拉等于把手动任务限制在"已知平台"里，
而那恰恰是它要解决的问题。所以来源恒为「手动」，你填的平台名原样显示。

安全上有一条硬约束：**手动任务绝不能进同步的「缺席判定」**——
同步层会对「本轮上游没看到」的任务累计缺席、够轮次就软删除，而手动任务上游
永远看不到。所以它挂在一个不出现在账号列表里的独立来源下，天然绕开所有同步逻辑
（有专门的测试守着这条线：连跑三轮同步后它必须还在、且缺席计数为 0）。

### 2. 截止提醒进通知栏

**提醒时刻**（按你选的方案）：

| 类型 | 提前量 |
|---|---|
| 作业 / 测验 | 截止前 **24 小时**、**12 小时** |
| 考试 | 截止前 **3 天**、**24 小时**（不可补交，值得更早） |

每个任务单独一条通知，点开直接进应用。

**关键：通知由系统闹钟发出，不需要 App 在运行。**

这条必须说清楚，因为它决定了实现方式。提醒的时刻（截止前 24 小时）你几乎肯定
没打开 App，而引擎跑在 WebView 的 JS 里 —— App 被划掉后 JS 定时器就不存在了。
所以：**JS 算排期 → 原生用系统闹钟注册**。到点由系统叫醒我们弹通知，
**App 没打开、被划掉、甚至正在重启都不影响**。

三个细节：

- **夜间不打扰**：很多平台把截止时间设成 23:59，那么"截止前 24 小时"正好是
  前一天深夜 23:59 —— 弹了你也不会看。所以 **22:00–08:00 的提醒自动顺延到早 8 点**；
  顺延后如果已经过了截止时间，这条提醒直接丢弃（迟到的提醒只会制造焦虑）。
- **不补发**：已经过去的窗口不补。否则每轮同步都会在那一刻突袭你一条通知。
- **重启恢复**：系统闹钟在手机重启后会全部丢失，所以排期存在本地、开机自动恢复。

**首次会弹一次通知授权**（Android 13+ 必须）。如果被拒了，待办页会显示一条
橙色提示，点它直接跳到系统设置里打开 —— 否则提醒功能整个不生效，
而症状是"什么都没有发生"，最容易让人以为自己记错了。

待办页底部还会显示「截止提醒已排期 N 条 · 下一条 X 月 X 日 HH:MM」，
让这条完全异步的链路有个可核对的地方。

## 四十五、0.1.39 更新（2026-10-08，iSmart 掉登录排查 + 添加待办改为独立层）

### 1. iSmart 掉登录：查到哪一步了

你给的时间点很有用：**10:52 最后一次请求，13:01 打开已是掉线状态**（间隔 2 小时 9 分）。

先把结论摆出来，再说依据：

> **大概率是 iSmart 服务端的会话「闲置超时」**（一段时间没有请求就作废），
> 不是我们弄丢了 cookie。**但这一点还不能 100% 确定**，所以这轮加了取证手段
> （见下），下次复现就能一锤定音。

三条依据：

1. **我们这边没有任何"主动让它过期"的逻辑**。iSmart 的会话没有过期时间字段，
   引擎手里的 `forceAuthProbe`（"强制探测会话"）虽然早就写好，但**从来没有被接上过**
   —— 也就是说同步时根本不会主动去验证会话，会话是否有效完全取决于平台怎么回。
   所以掉线的判定一定来自平台。
2. **实测确认 school 域的登录态是服务端会话**：未登录时请求 `currentuser` 返回
   `{"result":{"code":-21,"msg":"没有登录"}}`，同时给出一个 `serverTicketUrl`
   （SSO 票据换取地址）。这种结构说明登录态存在服务器上、由一枚会话 cookie 标识。
3. **cookie 的落盘是做了的**（原生侧在同步后和切后台时都会 flush），
   所以"重启后 cookie 丢了"这条最常见的原因可以先排除——不过这正是需要取证的那一半。

**2 小时这个数字值得注意**：它和 web 服务端会话的闲置超时常见值（120 分钟）高度吻合。
如果是闲置超时，那么**只要在这段时间里有请求，会话就能续下去**。

**这轮做的两件事：**

- **每轮同步开始前先探测一次会话**（iSmart 专属能力开关）。
  以前是"直接去拉数据，失败了再说"，会话失效要跑完课程才被发现；
  现在第一个请求就能识别，不白跑后面的请求。而且——**探测本身就是一次请求**，
  所以如果你常用这个 App，它同时起到了"续活"的作用。
- **掉线时附上 cookie 名单**（只报名字、不报值）。失败信息里会出现
  `〔CookieManager: …〕`，这是决定性的判据：
  - 名单里**还有**会话 cookie → 平台把这枚会话作废了（只能重新登录，无解）；
  - 名单里**没有**会话 cookie → 是我们把会话弄丢了（那就能修）。

所以下次掉登录时，把带 `〔CookieManager: …〕` 的那条日志截图发我即可定论。

### 2. 添加待办：入口挪到顶部，并改为独立添加层

按你给的第二个方案（独立添加页）做了，但没有新增底部标签——
底部已经有 5 个标签，再加一个会让每个都变窄，而"添加"是一次性动作、不是常驻去处。

现在的形态：**待办页顶部一个细入口「＋ 添加待办」→ 点开一个整屏添加层 →
填完保存（或取消）自动返回**。

为什么不做"原地展开"：待办列表是这一页的主体，在它上下展开表单会把列表整体推走，
用户填完回来时原来看到的位置已经不在屏幕上了（长列表下尤其明显）。
独立层不改变列表的布局和滚动位置，填写时也不用担心键盘把列表挤变形。

**`SESSION` 和 `CASTGC` 都还在。** 也就是说：

- 但平台在校验后仍然拒绝，返回登录页。

**所以是 iSmart 服务端把那一层会话作废了**，而不是本地保存出问题。

这与 web 服务端会话的**闲置超时**（常见值 120 分钟）高度吻合。
**结论：我们这边没有可修的缺陷，这是平台的行为。**

### 但发现了一条可能"自动续上"的路

顺着 `currentuser` 未登录时返回的那个 `serverTicketUrl` 摸下去，实测发现：

```
POST https://sso.ismartlearning.cn/v1/serviceTicket   (表单: service=…)
→ {"result":{"code":-23,"msg":"找不到tgt"}}
```

**这个端点存在、要 POST、靠 CASTGC 认人** —— 而你的 CASTGC 还在。
也就是说：**只要总票据还有效，就有可能自动换一张新的访问票据、把会话重建起来**

下次它掉线时同步一次，看这段就够了：

## 四十七、0.1.42 更新（2026-10-08，iSmart 自动续登 —— 掉线对你不再可见）

### 你的探测结果：`code=-25 msg=生成st失败`

这比我预期的更有价值。因为**没带票据时它报的是 `-23 找不到tgt`**，
而这次报的是 `-25 生成st失败` —— 说明服务端**认出了总票据**（找到了 TGT），
只是在生成服务票据那一步失败了。也就是说：**路是通的，是我给错了一个参数。**

### 找到真实路径了

顺着 school 域入口跟踪 302 跳转链，看到了浏览器的真实行为：

```
GET https://school.ismartlearning.cn/
  → 302  https://sso.ismartlearning.cn/login?service=https%3A%2F%2Fschool.ismartlearning.cn%2F
  → 302  http://me.ismartlearning.cn/front/login.html   （没有总票据时才到登录页）
```

两个关键点：

1. **正确入口是 `GET /login?service=<本域地址>`**，而且 `service` 必须是
   **本域地址本身**（`https://school.ismartlearning.cn/`）——
   我上一轮填的是登录页地址，那正是 `-25` 的原因。
2. **这条链在原生桥里就能走完**：桥是逐跳处理重定向的，并且把每一跳的
   Set-Cookie 都写回 CookieManager（当初写这个桥就是为了防"登录 → 302 → 主页
   才下发会话"丢会话）。所以**不需要打开网页、不需要用户做任何事**。

### 现在的行为：掉线会被自动接回，你根本不会知道

同步前探测发现会话失效 → 自动发一个 GET 走完换票链 → 会话重建 → **同步继续**。
全程不需要你点任何东西、也不会弹出任何错误。

- **接得回来**（总票据还有效，通常如此）：你看到的就是"同步正常完成"，
  不会知道中途曾经掉过线。
- **接不回来**（总票据也过期）：才报会话失效，并附上失败原因，
  引导你点「一键重登」。

另外，**「一键重登」现在也走 SSO 入口而不是登录页**：总票据还在时它会直接放行，
你连账号密码都不用输（通常连验证码都不用）。

> 实测观察：本层会话约 2 小时闲置就作废，但总票据的寿命长得多 ——
> 所以只要总票据还在，掉线对你就是不可见的。

### 顺带修了「信息超出屏幕宽度」

你截图里账号卡右侧被切掉，是 flex 的经典问题：卡片左侧那一列默认
`min-width: auto`，遇到**一长串没有空格的文本**（换票 URL、长 cookie 名）
时拒绝收缩，于是把整张卡撑出屏幕。已修：左列可收缩 + 文本按任意位置换行。

## 四十八、0.1.43 更新（2026-10-09，自动接回被错误码掐掉 —— 真机 bug 修复）

### 先认错：上一版说的"掉线对你不再可见"，在真机上并没有生效

你这次的两张截图（15:51 仍然报会话失效 + 日志里**请求只有 1 个**）
说明自动接回**根本没运行**。顺着"请求 1"这个数字查下去，找到了原因：

> iSmart 会话失效时，探测接口返回的是 **HTML 登录页**（不是 JSON）。
> 解析层把它抛成 `CAPTCHA_REQUIRED`（"疑似返回登录/验证页面"），
> 而探测函数**只吞 `AUTH_REQUIRED`** —— 于是这个错误一路冒泡，
> 上层"自动接回"的代码**连一行都没执行到**。

这解释了截图的全部三个特征：报错原文、请求只有 1 个、没有任何附注。

### 修复（三处，从窄到宽）

1. **探测函数的吞错范围**：探测的唯一目的是回答"会话还能不能用"，
   所以任何"需要重新登录"的形态都该回答"不能用"，而不是往外抛。
   现在 `AUTH_REQUIRED` / `AUTH_FAILED` / `CAPTCHA_REQUIRED` 三种都算"不能用"。
2. **引擎兜底**：把探测本身抛错的情况也纳入自动接回路径。
   这条防线必须由引擎兜住 —— 不能指望每个适配器都把错误码穷举对
   （这次就是漏了一个码，代价是整个机制静默失效）。
3. **错误分类修正**：网络故障不再被伪装成"需要重新登录"。
   分类错了，用户接下来做的事就全错（该查网络却去重登）。

### 自动接回现在会留下痕迹

以前接回成功是**完全静默**的，你只能靠"这次没报错"去推断 ——
而一个从不留下证据的机制，既没法验证也没法信任。现在日志里会写：

> 会话曾失效，已自动接回（无需你操作）

这次排障我一度判断"你装的不是最新版"（依据是请求数），是错的。
根因是**没有一个地方能直接看出装的是哪一版**——只能靠行为反推。
现在标题"课业中枢"旁边会显示 `v0.1.43`（从 APK 里读的真实版本，不是写死的常量）。
